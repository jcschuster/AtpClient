# Contributing

Thanks for taking an interest. This page says how the repository is set up, what
CI checks, and how a change gets in. Design notes for the code itself are in
[`CLAUDE.md`](CLAUDE.md), which is written for a coding agent but is the most
precise description of the architecture there is.

## Before you start

Open an issue for anything beyond a small fix, so the shape can be agreed before
the work is done. Bug reports are most useful with the system's actual output
(`result.output`): the library reads verdicts from what systems print, and the
text is the evidence.

## Setting up

The toolchain is in `.tool-versions` (Erlang and Elixir; any `~> 1.20` Elixir
works). Then:

```bash
mix deps.get
mix test                    # the default suite; the gated tags below are excluded
mix credo --all
mix dialyzer                # slow the first time, cached after
mix docs                    # ExDoc into doc/
elixir scripts/check_versions.exs   # every version mention agrees with mix.exs
```

Four tags need a live service and are excluded by `test/test_helper.exs`:

| tag | needs |
|---|---|
| `local_prover` | a prover binary on `PATH` (`scripts/build_eprover.sh` builds E into `priv/bin`) |
| `isabelle_server` | a running `isabelle server` (`ISABELLE_PORT`, `ISABELLE_PASSWORD`) |
| `starexec_live` | a StarExec instance (`STAREXEC_URL`, `STAREXEC_USER`, `STAREXEC_PASS`) |
| `sotptp_live` | tptp.org |

`mix test --include local_prover` runs one of them. The container that
`.claude/Containerfile` describes has all four services; outside it, run the
ones you can.

## What CI checks

`ci.yml` runs on every push to `main` and every pull request: version mentions,
`mix format --check-formatted`, `mix deps.unlock --check-unused`, a forced
`mix compile --warnings-as-errors`, Credo, `mix docs --warnings-as-errors`,
`mix hex.build`, the suite on two toolchains, the `local_prover` tests against E,
and Dialyzer. A pull request has to be green. `live.yml` runs the tptp.org and
Isabelle suites weekly; `systems.yml` refreshes the SystemOnTPTP snapshot nightly
(below).

## Conventions

- **Documentation.** Every public module, function and type is documented;
  `mix docs --warnings-as-errors` catches a broken reference.
- **No atoms from input.** Prover output is untrusted and the atom table is
  finite. An SZS word is resolved through `Tptp.Szs.Ontology`; anything the
  ontology does not define stays a binary.
- **Backends send what they are given.** A backend never parses its input; the
  direct path from TPTP text to prover copies nothing. Readings of the output
  (`Result.derivation/1`, `interpretation/1`, ...) run on demand, never in
  `query/2`.
- **Fixtures** under `test/fixtures/` are captured from real systems, and
  `test/fixtures/README.md` records where and when each came from. Add a row for
  every new one; do not hand-edit a captured file.
- **The system snapshot** `priv/system_on_tptp/systems.json` and `SYSTEMS.md` are
  generated by `mix atp_client.systems.refresh` from tptp.org's own records.
  Nothing in the source tree maps a system name to a kind; the one hand-maintained
  file is `priv/system_on_tptp/overrides.json`, and every entry there says why it
  exists (`reason`, `since`). `mix atp_client.systems.audit` lists what still
  needs one.
- **CHANGELOG.** User-visible changes get an entry under `[Unreleased]` in
  `CHANGELOG.md` ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/)).
  The version numbers everywhere else (`mix.exs`, `CITATION.cff`,
  `.zenodo.json`, the README's dependency line) are checked by
  `scripts/check_versions.exs`; leave them to the release.

## Releasing (maintainers)

1. Set `@version` in `mix.exs`; move the `[Unreleased]` entries into a
   `## [x.y.z] - date` section; set `version`/`date-released` in `CITATION.cff`
   and `version` in `.zenodo.json`. `elixir scripts/check_versions.exs vx.y.z`
   must pass.
2. Push the tag `vx.y.z`. `release.yml` verifies, publishes to Hex through its
   workload identity (the `hex` environment's reviewer approves), and drafts the
   GitHub release from the CHANGELOG section.
3. Publish the draft. That is what makes Zenodo mint the version's DOI under the
   concept DOI the README and `CITATION.cff` carry.
