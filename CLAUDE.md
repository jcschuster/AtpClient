# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`atp_client` is an Elixir library exposing a single, normalized interface to four backends for automated theorem provers:

- **`AtpClient.SystemOnTptp`** — public `tptp.org` HTTP form API.
- **`AtpClient.StarExec`** — self-hosted StarExec (Tomcat) instances, driven through the same URLs the web UI uses.
- **`AtpClient.Isabelle`** — `isabelle server` over the `:isabelle_elixir` package.
- **`AtpClient.LocalExec`** — locally installed TPTP-compliant binary (E, Vampire, …) invoked via `Port.open/2`.

The library sits on [`tptp`](https://github.com/jcschuster/tptp) (`{:tptp, "~> 0.2"}`), which owns the TPTP language: reading, linting, printing, and the SZS ontology and status-line reader. AtpClient is the transport to the provers and never parses what it sends.

Every backend takes an `AtpClient.Input` (a protocol: `binary()`, `iodata()`, `Tptp.File`, `Tptp.Unit`, `Tptp.Derivation`, `AtpClient.Interpretation`; `AtpClient.Problem` is its deprecated 0.8 shim, removed in 0.9) and returns `{:ok, %AtpClient.Result{}}` or `{:error, reason}`. `Result.status` is a `Tptp.Szs.Ontology` value read from the system's output by `AtpClient.Verdict` (SZS status line via `Tptp.Szs.status/1`, then SystemOnTPTP's `says` summary, then prover-specific patterns); `evidence` says how it was read (`:szs`, `{:pattern, text}`, `{:backend, module}` for Isabelle, `{:tstp, "Result"}` from a TSTP header, `{:system_info, key}` from the system's own `Solved` pattern); `output` is the raw output; `blocks` the delimited SZS output blocks; `Result.proof/1` reads a proof block as TPTP. A status word outside the ontology is `{:error, {:unknown_szs_status, word}}` — atoms are never created from prover output. Backend-specific error shapes (Isabelle's `{:isabelle_failed, …}`, LocalExec's `{:prover_not_found, …}`) are documented on each module.

Every backend additionally implements the `AtpClient.Backend` behaviour, which gives a Smart Cell or other UI a uniform handle: `config_key/0`, `label/0`, `config_schema/0` (a list of `AtpClient.Config.Field` structs), `verify/1`, and `query/2`. `AtpClient.backends/0` enumerates the four modules so UIs can discover them without hard-coding the list. `AtpClient.query/3` wraps a backend's `query/2` with the optional `preflight: true` (`AtpClient.preflight/1` = `Tptp.analyze/2`, rejecting on any error diagnostic); no backend parses on its own. Per-backend low-level entry points (`query_system/3`, `prove_theory/4`, `create_job/3`, `LocalExec.query_file/2`, …) remain available for callers that want sessions, multi-system fan-out, per-lemma detail, or a file passed to a prover by path.

## Commands

```bash
mix deps.get                       # fetch dependencies
mix compile
mix test                           # default suite; :local_prover tests are excluded
mix test --include local_prover    # also run the gated real-prover integration tests
mix test path/to/file_test.exs:42  # single test by line number
mix credo --all                    # lints
mix dialyzer                       # type checks (slow first run)
mix docs                           # ExDoc → ./doc/
scripts/build_eprover.sh           # builds E from source into priv/bin/eprover (for LocalExec)
elixir scripts/check_versions.exs [vX.Y.Z]  # every version mention agrees with mix.exs (and the tag)
```

Fixtures under `test/fixtures/` are captured live; their provenance (request, date) is in `test/fixtures/README.md` — add a row for every new one. Tests tagged `:local_prover` require a real prover binary on `PATH` (see `test/atp_client/local_exec_test.exs`); `:isabelle_server` a running Isabelle server (`ISABELLE_PORT`, `ISABELLE_PASSWORD`); `:starexec_live` a StarExec instance (`STAREXEC_URL`, `STAREXEC_USER`, `STAREXEC_PASS`, optionally `STAREXEC_SPACE_ID`/`STAREXEC_QUEUE_ID`); `:sotptp_live` tptp.org. `test/test_helper.exs` excludes all four by default.

## CI

`.github/workflows/`: `ci.yml` (push to main, PRs) runs `check_versions.exs`, format, `deps.unlock --check-unused`, a forced `compile --warnings-as-errors`, credo, `docs --warnings-as-errors`, `hex.build`, the default suite on `.tool-versions` and on OTP 29/Elixir 1.20, `--only local_prover` against E 3.5.1 built by `scripts/build_eprover.sh` (cached by tag), and dialyzer. `live.yml` (weekly, manual) runs `--only sotptp_live` and `--only isabelle_server`, the latter against Isabelle2025-2 copied out of `makarius/isabelle` and started in the background — `isabelle server -n` stays in the foreground once it has started one, so `isabelle server -l` is polled for its line. StarExec is not run in CI: it is a podman sidecar of the claude-env container (below), which a hosted runner does not offer. `release.yml` (tag `v*`) runs `check_versions.exs` with the tag (which also requires an empty `[Unreleased]`), the tests, then `mix hex.publish` in the `hex` environment (a required reviewer approves it) through Hex's workload identity — the job's GitHub OIDC token is exchanged for a 15-minute Hex token scoped to `package:hexpm/atp_client`, so no API key is stored; the identity on hex.pm (package page, "Workload identities") must name `jcschuster/AtpClient`, `release.yml` and `hex` — then drafts the GitHub release from the CHANGELOG section; publishing the draft is what makes Zenodo mint the DOI, so a person does it. `systems.yml` is the nightly snapshot refresh (below). `config/config.exs` sets `auto_refresh: false` in the test env only: the tests set `Systems` state themselves, and a refresh landing mid-run would replace it.

## Container

`claude-env init atpclient` (a NixOS-provided podman wrapper) writes `.claude/Containerfile`, which has every backend locally: `eprover`, `eprover-ho` (E 3.5.1), `vampire` (5.1.0) on `PATH` for LocalExec; Isabelle2025-2 under `/opt/isabelle` (`eval "$(isabelle-server-env)"` starts a resident server and exports `ISABELLE_HOST`/`ISABELLE_PORT`/`ISABELLE_PASSWORD`); a StarExec sidecar on `http://localhost:7827` with `STAREXEC_URL`/`STAREXEC_USER`/`STAREXEC_PASS` set in the container; and AtpMcp registered with Claude Code, configured by `.claude/atp_mcp.exs`. Run the gated suites there with `mix test --include local_prover --include isabelle_server --include starexec_live`.

## Configuration layering

`AtpClient.Config` resolves settings by merging, in increasing precedence:

1. Library defaults declared in `mix.exs` under `application/0 -> :env`.
2. Application env (`config :atp_client, :<backend>, …`).
3. Per-call `opts` keyword list.

Use `Config.fetch!(backend, key, opts)` for settings without sensible defaults (`:base_url`, `:password`, `:local_dir`, `:binary`) and `Config.fetch(backend, key, default, opts)` for everything else. Any new backend setting must be declared in `mix.exs` `:env` for the defaults layer to work.

## Application supervision

`AtpClient.Application` starts:

- `AtpClient.TptpFinch` (Finch pool, HTTP/1.1, TLS 1.2, verified) used by `SystemOnTptp` POSTs.
- `AtpClient.SystemOnTptp.Systems` (Agent of `AtpClient.System` records) — always started, from the shipped snapshot; `config :atp_client, :sotptp, auto_refresh: true` (the default) adds the background refresh.

The Isabelle, StarExec, and LocalExec backends are stateless from the supervisor's point of view; sessions (`AtpClient.Isabelle.Session`, `AtpClient.StarExec.Session`) are owned by the caller. The Isabelle session indirects through a private `AtpClient.Isabelle.SessionOwner` GenServer that holds the link to `IsabelleClient.Shared` — non-trapping callers therefore survive a failed `open_session/1` (it returns `{:error, reason}` rather than killing them) and a later Shared crash, and the owner monitors the caller so dropping the handle shuts the remote session down cleanly. Always pair `open_session/1` with `close_session/1` (or use the `query*` wrappers, which do this in an `after` block). `:dirs` reaches Isabelle's `session_start` as `session_args: [dirs: …]` on `IsabelleClient.Shared.start_link/1` — `isabelle_elixir` has no top-level `:dirs` option, and `Shared` builds the `session_start` arguments from `:session_args` plus `:session`.

## Backend specifics worth knowing

- **Isabelle filesystem coupling.** The Isabelle server cannot accept theory text over the wire; `prove_theory/4` writes `<local_dir>/<name>.thy` and tells Isabelle to load it from `master_dir = isabelle_dir`. `local_dir` (BEAM-side path) and `isabelle_dir` (path as the Isabelle server sees it) differ in containerised or Cygwin setups; `isabelle_dir` defaults to `local_dir` when unset. The `{:isabelle_failed, …, hints}` shape from `prove_theory/4` carries both paths back when "Cannot load theory file" appears.
- **TPTP → Isabelle.** `Isabelle.query/2` / `prove_tptp/3` route TPTP/THF problems through `IsabelleClient.TPTP.isabellize_theory/1` and prepend `unbundle from_TPTP`. The bundled `TPTP.thy` is copied into `:local_dir` on first use. Every Isabelle proving call returns a `Result` whose `evidence` is `{:backend, AtpClient.Isabelle}`: `prove_theory/4` carries the `use_theories` payload in `details.payload`; the per-lemma calls (`prove_lemmas/4`, `query_lemmas/3`, `prove_tptp/3`, `query/2`) put `[%{name, status}]` in `details.lemmas` and fold them weakest-link into `status` — `:theorem` only if every lemma was discharged, `:gave_up` for an empty list. Line numbers are not exposed; they would refer to the generated theory. The classifier over Isabelle's messages is `AtpClient.Isabelle.Verdict`.
- **SystemOnTPTP systems.** A system is given by name (`"E"`) or identifier (`"E---3.5.1"`); `AtpClient.SystemOnTptp.Systems.resolve/2` turns a name into the latest advertised version and checks an identifier as written. `Systems` is an Agent of `AtpClient.System` records that starts from the shipped snapshot `priv/system_on_tptp/systems.json` and, under `auto_refresh: true`, replaces it in the background from the SystemInfo report (`SystemOnTptp.SystemInfo.fetch/1`: `ListSystems`, then `ReportSelectedSystems`); a failed refresh logs and keeps the snapshot. Unknown systems are `{:error, {:unknown_system, name}}` and are never submitted: SystemOnTPTP stops at the first system it does not know. Each entry point checks the record's interfaces first — `query_system/3` needs `:system_on_tptp`, `process_problem/3` `:system_b4_tptp`, `process_solution/3` `:system_on_tstp` — else `{:error, {:not_offered, id, interface}}`. `query_selected_systems/3` sends the form as an ordered **list** (a map sorts the fields and reorders the systems), and merges the reply back onto the caller's list, so a system the server dropped is `{:error, :no_output}` rather than missing. `query/2` runs `:default_system`, library default `"E"`.
- **Reply shapes.** `X2TPTP=-S` (`:x2tptp`, default `true`) makes the reply one TSTP solution file per system; `false` gives the raw shape. `SystemOnTptp.Reply.sections/1` splits either: TSTP sections start at a rule followed by `% File :` (id = the `File` value); raw sections are `% START OF SYSTEM OUTPUT` … `% END OF SYSTEM OUTPUT` plus the `% RESULT:` / `% OUTPUT:` lines after (id = the `<sys>` of `% RESULT: <p> - <sys> says`). A `% RESULT:` line *inside* the delimited output is the system's own (GDV prints one per inference). A system that did not run has no TSTP section and, raw, summary lines only. `read_section/2` reads a TSTP section's `original` with `Verdict`, falls back to the header's `Result` (`evidence: {:tstp, "Result"}`), and keeps the solution in `details.tstp`.
- **Readings.** `Result.derivation/1`, `interpretation/1`, `formulae/1` (and the thin `proof/1`) are run on demand, never inside `query/2`. A derivation comes from `details.tstp.solution` else the first `Proof`-family block; an interpretation from the first `Interpretation`-family block (`Saturation` included), or for Isabelle from `details.nitpick` via `AtpClient.Isabelle.Nitpick`. `AtpClient.Interpretation.from_file/2` picks `Standard` / `VampireFmb` / `FiRoles` by what the file contains, never by system name; elements are stored unquoted so dialects compare equal, and `to_tptp/1` round-trips through `Standard`. `formulae/1` treats any `ListOf<X>` block (`ListOfCNF`, … — not ontology words) as `ListOfFormulae`. `AtpClient.verify/2` sends a derivation to GDV and an interpretation to AGMV via `process_solution/3`.
- **Capabilities and the override file.** `AtpClient.System.capabilities/1` derives `:prove`/`:find_model`/`:verify`/`:transform`/`:check`/`:import` from the record's fields (rules), then from `UserNote` keywords only when the rules give nothing — `:inspect` and `:verify_model` come from keywords only, since no field tells a viewer from a converter on SystemOnTSTP, nor a model verifier from GDV (`model verifier` always adds `:verify_model`), and an entry in `priv/system_on_tptp/overrides.json` (keyed by system **name**, `capabilities` + required `reason` + `since`) replaces both. That file is the one hand-maintained artefact: every entry says why it exists. `mix atp_client.systems.refresh` regenerates `systems.json` and `SYSTEMS.md`; `mix atp_client.systems.audit --strict [--previous old.json]` fails on a fallback-derived or empty system without an override, a stale or unadvertised override, or a `raw` word new since the previous snapshot. `.github/workflows/systems.yml` runs both nightly and opens the `systems/refresh` PR. No hand-written list of systems exists anywhere else.
- **Dialects.** `AtpClient.System.dialects/1` reads the record's `SPCs` (`E`: `TH0_NAR TX0_NAR TF0_NAR FOF CNF`) into `[{Tptp.Query.dialect(), components}]` — the form as the dialect, the rest (`NAR`, `CSA`, `NDT`, …) as written; `nil` without SPCs. A system's SPC word matches a problem's SPC when all its components are in it — that is SystemOnTPTP's `RecommendSystems` rule (iProver's `TF0_NDT` for `TF0_THM_NEQ_ARI_NDT`, observed 2026-10-15). `systems(dialect: d)` is plain membership, never `Tptp.Query.within?/2`: the records list every form they take, and tptp documents `within?` as no basis for prover acceptance. NX0/NX1 both read `:nxf` (NH0/NH1 `:nhf`) since `Tptp.Query` does not split them; the families `THF`/`TFF`/`TXF`/`NTF` (SPCForProblem's record) expand to their forms. The form table is `@forms`/`@families` in `lib/atp_client/system.ex`; the audit reports an unknown form as `{:unread_spc, word}`. Nothing checks a problem's dialect before sending it.
- **Req.** `~> 0.7`; the Finch pool is passed as `finch: [name: AtpClient.TptpFinch]` (the bare-name form is deprecated in 0.7).
- **StarExec auth quirk.** Tomcat's `FormAuthenticator` returns 408 if `j_security_check` is POSTed outside the protected area. `StarExec.login/1` first GETs `/starexec/secure/index.jsp` to obtain a JSESSIONID, then POSTs to `/starexec/j_security_check` — both paths are configurable, but the defaults are deliberate.
- **StarExec CSRF.** Current StarExec builds 403 any POST without the session's CSRF token. `login/1` reads it from the `csrf-token` / `csrf-header` meta tags of `session_init_path` once logged in (following its redirect to `explore/spaces.jsp`) into `Session.csrf`, and `request/4` sends it on every non-GET. Benchmark uploads there answer `202` with JSON progress instead of a 302.
- **StarExec solvers.** `StarExec.upload_solver/4` posts an archive (each `bin/starexec_run_<name>` inside becomes a configuration) to `/starexec/secure/upload/solvers` with `redirect: false` and reads the solver id from the `Location` of the 302 (`secure/details/solver.jsp?id=N`). Configuration ids come from `solver_configurations/3`, which scrapes `secure/details/solver.jsp` — StarExec's `services/details/solver/{id}` JSON does not expose configurations. Jobs (`create_job/3`, `prove/3`) take a configuration id, never a solver id.
- **LocalExec timeouts.** Two timeouts both fold into `{:ok, :timeout}`: the prover-side CPU limit (encoded in `:args` per prover, e.g. E's `--cpu-limit`) and a BEAM-side `Task.shutdown/2` wall-clock kill. `:wall_timeout_ms` defaults to `(cpu_timeout_s + 10) * 1000`. `LocalExec` does **not** inject a `--cpu-limit` flag — each prover's spelling lives in `:args`. The placeholder `"{{problem}}"` in `:args` is substituted with the temp file path; absent that, the path is appended last.
- **Reading output.** `AtpClient.Verdict.interpret/3` reads an SZS status line through `Tptp.Szs.status/1` **outside** output blocks (last line wins; a status line inside a block is data — ECNF prints `SZS status Unknown` inside its `ListOfCNF`), then SystemOnTPTP's `% RESULT: … <system> says <Value>` summary, then the system's own `Solved`/`GaveUp` patterns when passed as `solved:`/`gave_up:` (also consulted for an SZS word outside the ontology, e.g. AGMV's `Verified` → `:verified_good`), then the prover-specific pattern table (Alt-Ergo, E, LEO-II, SPASS, Vampire, Waldmeister). The table is grouped by system — each group lists the SystemOnTPTP `names` and LocalExec `binaries` it belongs to — and only the group of the system that ran is read (`Verdict.patterns/1`, from `:system_name`, else `:system`): Alt-Ergo's `": Unknown"` would otherwise read SystemOnTPTP's `ERROR: Unknown procedure` as a verdict for E. A system no group claims gets none; `nil` (no system known, e.g. StarExec without `:system`) gets all. `Systems.verdict_options/1` is what every backend passes for a system: its `Solved`/`GaveUp` patterns and `system_name`. A test checks every group name against the shipped snapshot. `:prefix` goes to `Tptp.Szs.blocks/2` (StarExec passes `Tptp.Szs.prefix(:starexec)`). Prefer a system's SystemInfo patterns over new `@patterns` entries; the table is expected to shrink. The LocalExec wall-clock kill appends `Tptp.Szs.status_line(:timeout, nil, "wall-clock kill by AtpClient.LocalExec")` to whatever the prover printed, so it reads like any other Timeout.

## Analyzers

`AtpClient.Analyzer.Tptp4x` implements `Tptp.Analyzer` (`id: :tptp4x`, `dialects: :any`): it posts the analysed source to TPTP4X on the configured SystemOnTPTP deployment and turns its `ERROR: Line N Char M …` lines into `Tptp.Diagnostic`s (code `"TPTP4X"`, offsets via `Tptp.Span.offset/3`). `analyze/2` returns `[]` when the deployment is unreachable; `check/2` returns the `{:error, reason}`. The local pass is `Tptp.Lint` via `Tptp.analyze/2`; the "skip the remote pass when the local pass has errors" rule is editor policy and lives in the caller (`Tptp.Diagnostic.any_errors?/1`).
